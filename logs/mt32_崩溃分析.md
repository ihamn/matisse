## 结果
- mt32 (63a19b0f): round1 rc=255 (exploit 退出), round2 崩溃重启 (17:37)
- run.out: task=ffffff80d6eb3780 cred_ptr=ffffff80d6eb3f00, attempt 1/4 fake_cred=ffffff80027b0ae0, 之后崩溃 (文件空字节)

## 关键观察
1. 写链修正后 (PSELECT_W* 生效), attempt 1 就崩 — 对比 mt30 (init_cred 不崩) 和 mt29 (假 cred attempt3 崩)
2. 崩得快 = 可能真的写到了 task+0x780 (cred 指针), 内核立即访问新 cred → panic
3. 但这不是"写落地成功"的确认 — 需要区分:
   a) 写到了 cred 指针 → 内核访问 init_cred 时崩 (写成功但副作用崩)
   b) 写链还是不对 → 野写崩 (没写对)

## 关键对比: ghostlock 写 child_task vs 我们写 perf 泄露 task
- ghostlock: 专门 fork 一个阻塞的 child 进程, 写它的 cred → 访问频率低 → 不崩
- 我们: perf 泄露的 task (可能是活跃任务, 如 sleep 进程) → 写了 cred 指针立即被访问 → 崩

## 下一步假设 (待验证)
- 如果写"活跃任务"的 cred 必崩 → 应该像 ghostlock 一样: spawn 一个阻塞子进程, 用 perf 找它的 task, 写它的 cred
- 我们代码里有没有 spawn 阻塞子进程 + perf 找它的路径? (ghostlock 的 spawn_child + child_main)
